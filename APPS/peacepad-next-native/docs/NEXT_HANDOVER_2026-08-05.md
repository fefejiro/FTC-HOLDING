## Attachment-intent boundary

### Proven now

- authenticated fictional staging actor;
- family and conversation participant checks;
- `records:write` check for private-binder metadata;
- four allowed media types;
- 25 MB maximum;
- bounded filenames and control/path character rejection;
- ten-minute expiry value;
- idempotent replay for an equivalent call path;
- metadata-only persistence;
- `status: metadata-prepared`;
- `uploadTransport: disabled`;
- `uploadUrl: null`;
- database constraints preventing enabled transport or completed status;
- safe audit metadata without the filename or bytes.

### Must be fixed before SourceArtifact work

1. Add one strict runtime request schema for the complete discriminated union.
   Reject unknown fields, nulls, arrays, wrong primitive types, unsafe integers,
   malformed targets, and Unicode control characters with a stable 400 error.
2. Add `findPrivateBinder(binderId)` and require matching family, actor owner,
   and active status. Family-level `records:write` is not binder ownership.
3. Store a request fingerprint with the idempotency receipt. Equivalent replay
   returns the original result; a different payload returns
   `409 IDEMPOTENCY_CONFLICT`.
4. Persist explicit nullable `conversation_id` and `private_binder_id` fields,
   require exactly one target, and enforce target existence in the same
   transaction using foreign keys where possible.
5. Add atomic expiry, cancellation, receiving, and single-use consumption
   behavior. A terminal intent cannot be reused or moved backward.
6. Partition or scope the hash-linked audit chain by at least region and family
   before production scale. Keep the claim narrow: the chain supports tamper
   detection, not authorship, truth, admissibility, or legal outcome.

Required adversarial tests include null, arrays, numeric filenames, negative or
fractional sizes, oversized integers, malformed targets, control characters,
cross-family access, cross-binder access, archived/revoked binders, equivalent
replay, conflicting replay, expiry, cancellation, duplicate consumption, and
status reversal.

No upload bytes belong in this hardening PR.

## SourceArtifact local proof

Begin only after attachment hardening passes and isolated staging is deployable.

Keep intent lifecycle separate from artifact processing:

| Object | State flow |
| --- | --- |
| Upload intent | `metadata-prepared -> receiving -> consumed` |
| Intent terminal outcomes | `expired`, `cancelled`, `rejected`, `failed` |
| Artifact ingestion | `receiving -> quarantined -> hash-verified -> scanning -> ready` |
| Artifact terminal outcomes | `rejected`, `failed` |

Required invariants:

- claim an unexpired intent atomically and only once;
- stream generated bytes to quarantine;
- sniff actual content instead of trusting the declared MIME or extension;
- calculate SHA-256 server-side while streaming;
- compare actual byte length with the declaration;
- preserve immutable original bytes;
- create artifact, audit event, and target link transactionally;
- re-read the stored object independently and verify the hash;
- keep derivatives separate;
- expose nothing before scan success and `ready`;
- use a simulated scanner and local private storage adapter only.

Required generated-byte tests:

- interrupted stream;
- wrong declared length;
- reused, expired, cancelled, cross-family, and cross-binder intent;
- PDF filename with unsupported content;
- duplicate identical bytes;
- same filename with different bytes;
- different filename with identical bytes;
- zero-byte input;
- corrupted re-read;
- scanner rejection;
- service restart between preparation and ingestion.

## Object storage gate

Only after local ingestion and staging gates pass:

- private region-specific bucket;
- encryption and object versioning;
- lifecycle and deletion policies;
- no public URLs;
- server-controlled authorized retrieval;
- backup/restore and hash verification;
- 25 MB server-mediated upload first, unless measured constraints justify a
  more complex client-direct design.

## User-facing attachment journey

The backend is not complete until the user can safely complete:

```text
Choose file
-> review metadata and destination
-> upload
-> scanning
-> ready
```

The interface needs progress, cancel, retry, safe rejection reasons, a clear
private-versus-shared destination warning, and a final state that does not
claim legal verification.

## Remaining security risks

- private-binder ownership is not proven by resource lookup;
- malformed runtime values can escape route validation;
- idempotency conflicts are not distinguished from equivalent replay;
- target existence is not relationally enforced;
- intent consumption and state reversal are not fully constrained;
- audit sequencing is globally coupled;
- deployed TLS, least privilege, concurrency, restore, and redaction are
  unproven;
- no real-device network proof exists;
- hosted checks are not independently executing;
- production authentication, migration, and privacy reconciliation remain open.
